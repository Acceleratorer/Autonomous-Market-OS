# U5.14 Cursor-Aware Catalog Sorting

**Status:** Implemented and measured locally on 2026-10-29.  
**Scope:** Avoid sorting catalog candidates that are already before an exclusive page cursor.

## Contract

The portfolio catalog still enumerates the full directory and preserves the
U5.11 stable ordering, recoverability checks, skipped-candidate count, stale
state handling, and page boundaries. On later pages, names at or before the
cursor are filtered during directory iteration, before eligible paths are
sorted. Sorting and cursor comparison both use case-sensitive portfolio ID
strings, consistently on every platform. The cursor is accepted only as a
direct child of the catalog root; symlink/reparse directories and policy files
are rejected, and broker open rechecks store containment before recovery. The
writer lock rejects linked files, including dangling links, and its parent is
revalidated before the lock is opened. Windows reparse attributes are checked
directly for Python 3.11 compatibility.

These checks reject pre-existing links and path escapes. They do not defend
against a hostile same-user process concurrently replacing store directories
between pathname checks and later file opens. The local filesystem account and
its permissions remain the trust boundary; hostile concurrent filesystem
mutation is outside the B4 local threat model.

This reduces path metadata checks, sort input, and temporary path allocation on
later pages. It does not reduce directory enumeration or skip validated cold
recovery for the cursor and displayed candidates. No cache, manifest, mtime, or
sidecar index is trusted.

## Verification

- Focused broker, shared-portfolio, operator, U5 acceptance, and
  application-surface tests: 65 passed. The drive-qualified path escape test
  ran on Windows using a drive different from the temporary store's drive.
- Python compile check, evidence JSON parsing, and `git diff --check` passed.
- A synthetic directory-tree harness compared the old full-sort-then-filter
  sequence with filtering before sorting. Each case measured five runs. Stable
  counts and diagnostic medians:

  | Candidate directories | Page | Entries scanned | Sort inputs before → after | Median before → after |
  |---:|---|---:|---:|---:|
  | 100 | first | 100 | 100 → 100 | 3.679 → 3.718 ms |
  | 100 | middle | 100 | 100 → 50 | 3.950 → 2.669 ms |
  | 100 | last | 100 | 100 → 1 | 4.056 → 1.308 ms |
  | 1,000 | first | 1,000 | 1,000 → 1,000 | 31.147 → 31.724 ms |
  | 1,000 | middle | 1,000 | 1,000 → 500 | 30.604 → 16.791 ms |
  | 1,000 | last | 1,000 | 1,000 → 1 | 31.941 → 3.039 ms |
  | 10,000 | first | 10,000 | 10,000 → 10,000 | 330.655 → 331.855 ms |
  | 10,000 | middle | 10,000 | 10,000 → 5,000 | 324.019 → 178.343 ms |

  The timings are local diagnostics without real broker recovery; they are not
  CI thresholds. Entries scanned remain linear in catalog size. Sort-input
  counts are the stable result: later pages sort only the suffix after the
  cursor.

## Remaining limits

Catalog directory enumeration remains linear, and the first page still sorts
all eligible names. Every cursor and displayed portfolio still undergoes full
validated cold recovery; current ledger and checkpoint rules do not provide an
independently trusted anchor for skipping replay. A durable catalog index or
cache requires a separate cross-process mutation, restore, rebuild, and
integrity contract. U5.5 connected deployment and B4 deletion/schema
transformation remain separate gates.
