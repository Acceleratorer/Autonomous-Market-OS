# B4.19 Local Mutation Capability Contract

**Status:** Implemented locally for the synthetic, paper-only Python boundary.
**Date:** 2026-10-29

## Purpose

B4.14 defines audited local broker mutations, but the compatibility broker
methods do not carry a caller capability. B4.19 adds a small in-memory local
capability seam for callers that need to invoke `submit_order`, `cancel_order`,
or `revoke_approval` without exposing HTTP or CLI mutation. This is local
capability authorization, not human authentication or an identity-provider
integration; `subject` is an issuer-bound claim until U5.5 defines a trusted
principal path.

## Boundary

- Synthetic, paper-only, local Python only.
- No network provider, Binance, credential store, live venue, production
  runtime, HTTP mutation route, or CLI mutation route.
- The existing JSONL ledger, checkpoint, fingerprint, recovery, and replay
  authority remain unchanged.
- `LocalMutationAuthority` is the capability-authorization seam. Direct broker
  methods remain trusted in-process compatibility APIs and are not an
  authenticated boundary.
- The signing secret exists only in caller/verifier memory. It is never written
  to a portfolio file, ledger payload, checkpoint, exception, or inspection
  response.

## Capability format

The token is a compact prefix plus two encoded values:

```text
b4.19.<base64url-canonical-payload>.<base64url-hmac-sha256>
```

The signed payload has exactly these fields:

| Field | Rule |
|---|---|
| `schema` | `market-os.b4-19.local-capability@v1` |
| `subject` | Stable bounded local caller identity |
| `portfolio_id` | Exact portfolio identity |
| `operation` | `order.submit`, `order.cancel`, or `approval.revoke` |
| `command_fingerprint` | Exact fingerprint of the command projection |
| `issued_at_ms` | Non-negative integer |
| `expires_at_ms` | Integer strictly after issue time |
| `idempotency_key` | Exact command idempotency key |

HMAC-SHA256 signs the encoded payload with a caller-supplied local secret. The
secret must be at least 32 bytes and is injected in memory; it is not a
credential store or a human-login mechanism. The signed payload has no
additional replay nonce: the existing command idempotency key is the durable
replay authority.
Verification uses constant-time signature comparison and rejects malformed,
unknown-field, forged, wrong-subject, wrong-portfolio, wrong-operation,
wrong-command, not-yet-valid, and expired capabilities.

The command fingerprint already binds stable strategy identity for shared
portfolios because the B4.15 order/cancel command projections include the
strategy ID where applicable. The capability does not duplicate mutable
strategy membership.

## Verification and ordering

1. The local caller constructs the exact command and its normal B4 fingerprint.
2. `LocalMutationAuthority` verifies the capability against a separately
   supplied trusted subject, operation, portfolio, command fingerprint, and
   idempotency key before calling the broker.
3. The broker takes its existing process and writer locks, checks its loaded
   ledger head, and applies the existing validation, reservation, ordering,
   idempotency, and append-only event rules.
4. A stale writer still fails closed and must reload. Capability validity does
   not override portfolio locking or stale-writer checks.
5. A retry with the same valid capability and command identity follows the
   existing idempotent replay path and appends no second event. A different
   command under the same idempotency key remains a conflict.

Capability rejection happens before command mutation and does not append a
command event because no authorized command was accepted. Once capability
verification succeeds, every broker acceptance or typed rejection retains
the B4.14 audit semantics.

## Audit and recovery

Authorized command events may include only this safe context:

```json
{
  "subject": "operator.example",
  "operation": "order.submit",
  "capability_fingerprint": "<sha256>"
}
```

The raw token, HMAC secret, and signature bytes are not persisted. Existing
ledger event fingerprints include the safe context, so recovery, checkpoint
validation, deterministic replay, audit inspection, and idempotent retry remain
equivalent for the authenticated command result.

## Failure and recovery rules

- A malformed, forged, or unverifiable capability fails closed before the
  broker is called.
- Subject, portfolio, operation, fingerprint, validity-window, and secret
  mismatches fail closed without changing ledger or checkpoint bytes.
- A broker rejection after successful capability verification is recorded by
  the existing typed rejection event and recovers identically.
- A concurrent writer is handled by the existing portfolio lock and stale
  snapshot rule; retry requires the caller to reload and create/use a valid
  capability for the same command identity.
- Capability replay is safe only for the same command identity. No separate
  nonce database is introduced; the existing append-only idempotency record is
  the durable replay authority.

## Explicit non-goals

This milestone does not authenticate a human or select an identity provider,
session cookie, network transport, public host, multi-tenant storage boundary,
distributed lock, credential manager, live trading path, or deletion/retention
behavior.
