# B4.2 Ledger and Recovery Integrity

**Status:** Implemented locally on 2026-10-26 as a synthetic, paper-only hardening slice.

**Purpose:** Close the smallest recovery-integrity gap after the approved B4.1 persisted broker slice while preserving the B4.1 storage format and public seams.

## Scope

- Validate every persisted ledger result snapshot's schema, portfolio identity, and fingerprint.
- Persist and verify a fingerprint for each event's resulting snapshot.
- Validate checkpoint schema, sequence, identity, fingerprint, and canonical equality with replayed ledger state.
- Keep adverse slippage from producing a limit fill outside its submitted limit price.
- Preserve deterministic recovery through `B41Broker.open()` and `B41Broker.recover()`.

## Public seams and evidence

The focused seams are `B41Broker.open()`, `B41Broker.recover()`, `B41Broker.inspect("replay")`, and the existing synthetic limit-order path. Regression coverage lives in [test_portfolio_broker.py](../market_os/tests/test_portfolio_broker.py).

Recovery rejects altered checkpoint snapshots, checkpoint sequence metadata, and ledger result-snapshot fingerprints. Limit orders remain open when adverse slippage would cross their limit. The ledger remains append-only JSONL with the B4.1 hash chain and atomic checkpoint write.

## Boundaries

B4.2 adds no provider access, live data, trading, network transport, new persistence backend, partial fills, expiry, portfolio sharing, or mutation API route. Numeric inventory, loss, drawdown, and loss-window values remain required policy configuration and fail closed when absent.

The B4.1 contract remains the source of truth for policy decisions. This document records only the B4.2 implementation slice and its evidence.
