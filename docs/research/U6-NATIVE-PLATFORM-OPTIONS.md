# U6 Native Platform Options: Tauri 2 vs Electron\n\n**Date:** 2026-11-03\n**Scope:** U6 native desktop platform gate after the U6.1 local Next.js shell slice\n**Sources:** Official Tauri and Electron documentation only\n\n## Repository fit\n\nThe current U6 surface is a server-rendered Next.js/Node.js shell over the local\nPython gateway. It is synthetic, paper-only, loopback-bound, GET-only, and has\nno provider credentials or mutation routes. A native shell must preserve the\nexisting Python/API/CLI envelopes and must not become a second domain authority.\n\nThe main integration question is gateway lifecycle: a desktop package must\nstart, monitor, and stop the local Python gateway (and, if retained, the local\nNext.js server) without exposing a public listener or secrets.\n\n## Comparison\n\n| Gate | Tauri 2 | Electron |\n|---|---|---|\n| Process model | A Rust **Core** process owns OS access and IPC; WebView processes render the UI. The WebView is supplied by the OS rather than bundled. [Process model](https://v2.tauri.app/concept/process-model/) | One Node-capable **main** process owns app lifecycle and native APIs; each `BrowserWindow` has a separate renderer. Chromium and Node are bundled with the app. [Process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Introduction](https://www.electronjs.org/docs/latest/) |\n| Runtime footprint | Usually smaller because WebView libraries are dynamically linked at runtime. Host differences must be handled: WebView2 on Windows, WKWebView on macOS, and webkitgtk on Linux. [Process model](https://v2.tauri.app/concept/process-model/) | Larger install/runtime because Chromium and Node ship with the app, but the rendering/runtime versions are controlled by the package and users do not need Node installed. [Introduction](https://www.electronjs.org/docs/latest/) |\n| Filesystem and privilege model | Frontend code reaches OS functions through commands and IPC. Capabilities, permissions, and scopes restrict which windows may invoke which commands. [Security](https://v2.tauri.app/security/), [Runtime authority](https://v2.tauri.app/es/security/runtime-authority/) | Sandboxed renderers must delegate filesystem/system/subprocess work to the main process over IPC. Electron requires context isolation, sandboxing, validated IPC senders, navigation limits, and no Node integration for untrusted content. [Sandbox](https://www.electronjs.org/docs/latest/tutorial/sandbox), [Security](https://www.electronjs.org/docs/latest/tutorial/security/) |\n| Local gateway lifecycle | The shell plugin can spawn a packaged sidecar; `processGroup` can terminate a child tree. Spawn/execute requires explicit shell capability permission. [Shell plugin](https://v2.tauri.app/reference/javascript/shell/), [Sidecars](https://v2.tauri.app/learn/sidecar-nodejs/) | The main process controls application lifecycle. `utilityProcess` provides managed Node child processes with spawn/exit/kill events; a Python gateway would need a main-process child-process integration rather than the JS-only utility-process fork API. [Utility process](https://www.electronjs.org/docs/latest/api/utility-process), [Process model](https://www.electronjs.org/docs/latest/tutorial/process-model) |\n| Packaging and desktop targets | Official distribution tooling covers Windows, macOS, and Linux packages including Debian, Snap, AppImage, Flatpak, RPM, and AUR. Most platforms require signing. [Distribute](https://v2.tauri.app/distribute/) | Officially targets Windows, macOS, and Linux and ships the runtime with the app. [Introduction](https://www.electronjs.org/docs/latest/) |\n| Updates and rollback | Updater artifacts require signatures. Static JSON feeds are supported, and version comparison can be configured to permit an explicit downgrade for rollback. [Updater](https://v2.tauri.app/plugin/updater/) | Built-in `autoUpdater` supports macOS and Windows; official docs state there is no built-in Linux updater and recommend the distribution package manager. [autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater/), [Updating](https://www.electronjs.org/docs/latest/tutorial/updates) |\n| Main implementation risk for this repo | Existing SSR Next.js/Node runtime would likely need a packaged Node/Next sidecar or a change to a static frontend; Rust and host-WebView dependencies add new build/release work. | Reuses the existing Node/Next stack most directly, but adds a broad Node-capable main-process boundary and a larger runtime; Linux update/rollback needs a package-manager or signed release policy. |\n\n## Recommendation\n\nSelect **Electron** for the smallest U6 implementation path if the goal is to\npackage the existing server-rendered Next.js shell with minimal architectural\nchange. Keep all filesystem and gateway operations in the main process, expose a\nsmall typed preload API, enable renderer sandboxing and context isolation, and\nallow only loopback navigation to the local shell/gateway. Treat Linux updates\nas a separate package-manager or manually promoted signed-release gate; do not\nclaim cross-platform auto-update from Electron's built-in updater.\n\nSelect **Tauri 2** instead if binary size and capability-level least privilege\noutweigh implementation speed. Its permission model is a better direct fit for\nU6's read-only boundary, but a short spike must first prove packaging the\ncurrent Next.js server and Python gateway as controlled sidecars, including\nstartup readiness, shutdown process-group cleanup, and failure recovery across\nWindows and Linux.\n\n## Smallest U6 gate\n\nThe platform ADR should choose one option and record:\n\n1. target desktop OSes and supported architectures;\n2. whether the existing Next.js server remains packaged or the shell becomes a\n   static frontend;\n3. Python/Node gateway startup, readiness, shutdown, and crash handling;\n4. filesystem permissions and the exact allowed local data root;\n5. installer signing, update source, downgrade/rollback behavior, and Linux\n   update policy;\n6. parity and safety tests that keep CLI, HTTP, Next.js, and native payloads\n   identical and preserve the local, paper-only, GET-only boundary.\n\nNo connected runtime, provider credential, mutation route, public listener, or\nlive execution path is part of this decision.\n
