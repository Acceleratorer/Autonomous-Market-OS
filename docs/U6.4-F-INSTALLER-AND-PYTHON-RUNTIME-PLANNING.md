# U6.4-F Installer and Python Runtime Planning

**Status:** accepted contract; implementation is authorized within the scope below
**Date:** 2026-11-15
**Related decisions:** U8-C permanent paper-only mode, ADR-0053, ADR-0054

## Purpose

Define the accepted scope for a native offline installer and embedded Python
distribution in the existing Electron artifact. The package remains portable,
per-user, manually launched, and service-free; platform mechanics stay behind
the existing artifact and preflight contracts.

## Current baseline

U6.4-C creates signed target-native directory artifacts for `windows-x64` and
`linux-x64`. U6.4-D validates an unpacked artifact without installing it.
U6.4-E copies that artifact through staging, publishes it with one rename,
resets artifact-local mutable storage, and revalidates the published tree.
U6.4-F adds an optional target-native CPython 3.11.x runtime bundle. CI freezes
one approved patch per target from python.org, builds the runtime from the
official target-specific archive, and records that archive hash plus the
runtime-manifest hash in
`python/runtime/runtime-manifest.json`.

The current CI pins CPython 3.11.9 for the Windows embeddable amd64 package and
CPython 3.11.14 for the Linux source build. The outer signed artifact binds the
runtime manifest hash, while the runtime tree hash binds the remaining runtime
files.

Python remains the authority for accounting, risk, persistence, recovery,
research inspection, and paper execution. Electron may supervise processes and
coordinate installation, but it must not become a second domain implementation.

## Boundary that remains fixed

U6.4-F is local and offline. It must preserve:

- synthetic and permanent paper-only operation;
- read-only inspection and mutation-disabled HTTP/CLI surfaces;
- loopback-only process communication;
- no credentials, provider requests, public listener, live trading, or U5.5
  owner-VM promotion; and
- the U6.4-D preflight and U6.4-E staging, verification, and rollback rules.

## Decision matrix

ADR-0055 accepts one row in each category below. The matrix is the
implementation contract; hosted CI evidence is the remaining acceptance gate.

| Category | Accepted decision | Status | Required evidence |
|---|---|---|---|
| Targets | `windows-x64` and `linux-x64`, using the existing U6.4-C runner and Electron support baseline. | accepted | Record exact runner images in CI evidence. |
| Windows package | Signed portable `tar.gz`; install from its verified extracted directory. | accepted | Preserve external-key signing and manifest hashes. |
| Linux package | Signed portable `tar.gz`; no distribution-specific service manager. | accepted | Preserve external-key signing and manifest hashes. |

## Installation interface seam

The future implementation should expose one small installation interface at the
Electron boundary. A target-specific adapter may satisfy that interface, but
callers should not know package-manager details:

```text
install(verifiedArtifact, targetPolicy) -> InstallResult
```

`InstallResult` must make the following inspectable without reaching into
Python internals: target, installed version, manifest digest, package/runtime
identity, destination paths, storage migration result, rollback record, and
boundary status. The adapter owns platform mechanics; the existing preflight,
manifest, signature, storage, and rollback checks remain authoritative.

The first implementation uses one portable adapter for both target-native
artifacts. A second platform-specific adapter is still unnecessary until the
accepted contract actually requires different mechanics.

## Accepted contract

The accepted versioned decision record fixes:

1. target operating systems, architectures, and minimum supported versions;
2. package format and signing/provenance inputs for each target;
3. per-user versus machine-wide scope and elevation behavior;
4. embedded Python version, build source, dependency layout, and offline check;
5. application, configuration, cache, and portfolio paths;
6. first install, upgrade, rollback, repair, and uninstall semantics;
7. service registration and launch lifecycle, if any;
8. install-result schema and evidence retention; and
9. failure, retry, interruption, conflict, and verification behavior.

Implementation is authorized only for this accepted offline, paper-only scope.

## Hosted acceptance gate

The hosted acceptance gate closes only after matching Windows and Linux CI
jobs demonstrate:

- signed package identity and reproducible manifest/tree digests;
- offline installation on a clean host or isolated fixture;
- fresh install, upgrade, failed verification, retry, rollback, and repair;
- preservation or migration of mutable state exactly as the contract states;
- uninstall behavior that leaves the documented user data state;
- no public listener, provider request, credential, mutation, or live path;
- Python remains the accounting and persistence authority; and
- machine-readable JSON and Markdown evidence is internally consistent.

## Explicit non-goals

This contract does not register a native service, change release slots, enable
connected access, or change the U8-C paper-only decision. It does add the
target-native runtime bundle and per-user portable installation path described
above.
