# U5.5 Authenticated Connected Web Contract

**Contract version:** `market-os.u5-5.connected-runtime-identity@v1`
**Status:** Locally verified, not enabled. Private single-tenant preview scope, Next.js stack, private Linux VM with systemd, and owner-only Tailscale Serve access path are selected; local application evidence passes, while owner-VM promotion and rollback remain pending.
**Scope:** Future private, authenticated, read-only web access over the paper API.

## Contract

The promotion state is monotonic:

```text
defined -> target_selected -> locally_verified -> enabled
```

The current state is `locally_verified`. A selected target or identity provider does
not become trusted merely because it is configured; the origin must verify the
assertion and apply the same authorization and storage checks on every request.

### Runtime and trust boundary

- A reverse proxy or private ingress terminates transport security and forwards
  only to loopback-bound Next.js and Python processes.
- Next.js is a read-only server-side adapter. Python remains the authority for
  portfolio recovery, accounting, reservations, fingerprints, and inspection.
- The Python gateway rejects direct non-loopback access and rejects caller
  supplied principal headers. Diagnostic `X-Request-ID` values never grant
  identity or authorization.
- A supervisor owns bounded restart, startup ordering, health checks, versioned
  promotion, and one known-good rollback slot. Health checks are read-only and
  must verify both processes before promotion.

### Principal assertion

The trusted ingress-to-origin envelope is versioned and contains only:

`issuer`, `subject`, `audience`, `issued_at`, `expires_at`, `jti`, and the
verified assertion method. `subject`, `issuer`, and `audience` are stable
bounded identifiers. The origin rejects missing, malformed, expired, replayed,
wrong-audience, wrong-issuer, and unverified assertions. Raw tokens and
signatures never enter portfolio ledger, checkpoint, snapshot, browser HTML,
or client bundles.

### Authorization and storage

- Authorization is server-side and object-scoped: `subject -> tenant ->
  portfolio_id -> inspection resource`.
- The allowlist is explicit, versioned, and fail-closed. An empty or stale
  mapping denies access; it never means “all portfolios”.
- The runtime may open only the configured portfolio root. Portfolio IDs and
  roots are validated before resolution; traversal, symlink/reparse aliases,
  descriptor/path replacement, and cross-tenant roots fail closed.
- Responses are bounded to the existing local inspection contracts and omit
  raw filesystem paths, secrets, capability tokens, and internal signing data.

### Owner-selected target

- Private Linux VM owned by the project owner, supervised by `systemd`.
- Owner-controlled private Tailscale tailnet using Tailscale Serve; only the
  owner's Tailscale identity may reach the browser ingress.
- One `owner-only` subject; portfolio allowlist is exactly `paper-main`.
- Fixed portfolio root:
  `/var/lib/autonomous-market-os/portfolios`.
- Session policy: 15-minute expiry, 60-second clock tolerance, revocable
  one-time `jti` replay state, fail-closed invalid/missing identity, and no
  mutation capability.
- Project owner owns backup/rollback. Promotion creates an encrypted backup,
  retains one known-good release slot, and leaves the current version active
  when health checks fail.

### Session, audit, rollback, and secrets

- Sessions are short-lived, revocable, bound to the verified subject and
  audience, and checked with a documented clock tolerance. `jti` replay is
  rejected after use or revocation.
- Denials, principal changes, portfolio decisions, direct-origin attempts,
  backup/restore actions, and rollback actions append bounded audit records with
  reason codes and correlation IDs. Secrets and raw assertions are redacted.
- Promotion is copy-on-write, health-gated, and interruption-safe. A failed
  health check keeps the prior known-good version active; rollback is explicit
  and auditable.
- Secrets are injected only into server processes through the selected host's
  secret mechanism, rotated without browser exposure, and excluded from
  `NEXT_PUBLIC_*`, HTML, manifests, source control, and logs.

### Abuse controls and evidence

The selected runtime must enforce request/body limits, per-subject and
per-origin rate limits, bounded timeouts, bounded page sizes, and generic error
responses. The v1 evidence matrix must cover:

| Case | Required result |
|---|---|
| valid assertion + allowed portfolio | bounded read-only response |
| missing, malformed, expired, replayed assertion | deny + audit reason |
| wrong issuer/audience or forged principal header | deny + audit reason |
| subject mapped to another portfolio | deny + no storage open |
| direct Python-origin request | deny + no principal trust |
| traversal/symlink/reparse storage alias | deny + no file disclosure |
| oversized body, page, or slow request | bounded rejection |
| failed promotion health check | prior version remains active |
| secret scan and browser-bundle inspection | no secret/token material |

Before a connected or public browser deployment can be enabled, the system
must define and verify:

- an authenticated subject identity and stable tenant/portfolio audience;
- authorization that maps a subject to permitted portfolio IDs and inspection
  resources;
- a defined subject set for the single tenant and a fail-closed identity
  propagation path from the chosen ingress through Next.js to Python;
- verification of identity assertions and an origin boundary that prevents
  unauthenticated direct access or spoofed principal headers;
- storage isolation per tenant or an equivalent partition boundary;
- same-origin or explicit allow-listed CORS behavior;
- session expiry, revocation, clock handling, and denied-request audit events;
- secret handling outside browser bundles, HTML, manifests, and request logs;
- rate limits, request size limits, timeout behavior, and abuse responses;
- production log retention, alerting, backup/restore, rollback, and operator
  access review;
- a paper-only default where any future mutation capability is separately
  versioned, authenticated, idempotent, audited, and disabled by default.

## Current state

The local gateway remains loopback-only, rejects untrusted `Host` headers, and
the connected mode is opt-in. Python trusts only the signed server-to-server
principal envelope; raw Tailscale or caller-supplied principal headers are not
identity. The Next.js connected proxy requires the configured Tailscale host,
owner identity, and GET/HEAD method, and permits only the `paper-main` operator
route plus process health/static assets. The separate DirectAdmin deployment
decision applies only to the disconnected static preview; see
[ADR-0046](decisions/ADR-0046-directadmin-static-market-os-deployment.md).

## Promotion criteria

Connected-access promotion may begin only after the selected target's versioned
API/auth test matrix covers allowed, denied, expired, replayed,
forged-principal, direct-origin, cross-portfolio, path-alias, abuse-limit,
secret-scan, health, backup, and rollback behavior. No credentials are
committed; deployment secrets remain host-injected.
