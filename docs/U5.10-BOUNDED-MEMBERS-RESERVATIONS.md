# U5.10 Bounded Member and Reservation Inspection

**Status:** Implemented and verified locally on 2026-10-29.  
**Scope:** Bound member and current-reservation rows in the local portfolio
detail response and expose independent read-only paging in both browser
surfaces.

## Contract

Both local browser surfaces now use
`GET /v2/b4/portfolios/{portfolio_id}/inspection`, returning
`market-os.b4-portfolio-inspection@v2`. The previous v1 aggregate remains
available for local compatibility and is unchanged.

- The compact `genesis` object omits `member_strategy_ids`.
- `members.strategy_ids` is sorted ascending and contains at most the requested
  page size. `member_after_strategy_id` is exclusive; `total_count` always
  describes the full membership set. An isolated portfolio exposes its one
  strategy through the same page shape.
- `reservations.reservations` contains only currently open reservations, newest
  first in broker order. `reservation_before_order_id` is exclusive and must
  identify an order that still has an open reservation. The cash, BTC, buy
  quantity, and `total_count` values always cover the full current reservation
  set, independent of the row page.
- Orders and risk outcomes keep the U5.9 projections and exclusive cursors.
  All four cursors are independent: `order_before_id`,
  `risk_before_sequence`, `member_after_strategy_id`, and
  `reservation_before_order_id`.
- Each page limit accepts integers from 1 through 100. The browser defaults are
  25 members, 25 reservations, 25 orders, and 8 risk outcomes.
- Unknown or repeated query parameters, malformed cursors, cursors absent from
  the relevant set, and invalid limits return HTTP 400. V2 exposes only this
  aggregate resource.
- Next.js validates the v2 schema, identity, page metadata, and row bounds
  before mapping values. The HTML shell uses text nodes and keeps each cursor
  when the operator changes another page.

Python remains authoritative for identity, order chronology, current open
reservations, and all totals. The web surfaces do not calculate financial
values or issue commands.

## Verification

- Focused broker, HTTP, and compatibility-shell checks: 42 passed.
- Next.js TypeScript check and optimized production build passed.
- Production browser smoke used a temporary synthetic portfolio with 30
  members, 27 open reservations, 37 orders, and 10 risk outcomes.
- Both surfaces moved through member and reservation pages while preserving
  independent order and risk cursors. The Next.js URL retained all four cursors
  after changing each page; the HTML shell retained all four in its next API
  request.
- At 375px, both documents fit the viewport. The shell's discovered min-content
  overflow was fixed by allowing grid panels and definition-list values to
  shrink and wrap; wide tables continue to scroll in their labelled regions.
- Browser console errors: 0. Screenshots are in `output/playwright/u5-10/`.

Machine-readable results are in `docs/evidence/u5-10-bounded-members-reservations.json`.

## Limits and next gates

- The v1 aggregate, legacy detail resources, and portfolio catalog remain
  compatibility routes; the v1 aggregate and catalog can still return
  cardinality-dependent membership/reservation data. Only the local browser
  detail surfaces have moved to bounded v2.
- Broker recovery and risk-page selection remain linear in ledger size.
- The legacy `/risk` resource still returns full history and must not be
  exposed through a shared or remote service.
- U5.5 still requires a concrete connected target, identity, tenant isolation,
  session and rate-limit rules, audit, backup, rollback, observability, and
  operator-access decisions.
- B4 retention deletion and versioned schema transformation remain separate
  contracts.

U5.10 adds no authentication, public listener, mutation route, credential,
provider call, real-data path, or live venue. The operator remains synthetic,
paper-only, loopback-only, and read-only.
