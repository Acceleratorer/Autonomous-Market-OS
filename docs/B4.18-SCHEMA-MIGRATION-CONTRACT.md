# B4.18 Versioned Schema Migration Contract

**Status:** Implemented and verified locally as a copy-on-write transformer with target-native recovery and source-projection replay equivalence; no automatic or connected migration.
**Date:** 2026-10-29
**Scope:** Synthetic, paper-only, local Python portfolio stores.

## Purpose

B4.12 classifies a recoverable store as current and never rewrites bytes.
B4.18 adds an operator-invoked transformer that produces a new validated
target envelope while preserving the source store and its append-only history.
Target validation recovers the v2 envelope directly, then independently replays
a source-shaped projection through the existing broker and compares semantic
state and inspection resources before promotion.

## Boundary

- Input is an existing local B4 portfolio store with a supported source schema.
- Output is a new local portfolio store with an explicitly named target schema.
- The source store is never edited, truncated, deleted, or replaced in place.
- No provider, network, credential, live venue, HTTP mutation route, or public
  deployment is part of this contract.
- Migration is an operator-approved local maintenance action, not an automatic
  startup behavior.

## Source and target identities

The first transformer may support only:

| Artifact | Current source identity | First target identity |
|---|---|---|
| Broker contract | `market-os.b4-1.paper-broker@v1` | `market-os.b4-18.paper-broker@v2` |
| Isolated genesis | `market-os.b4-1.paper-portfolio-genesis@v1` | `market-os.b4-18.paper-portfolio-genesis@v2` |
| Shared genesis | `market-os.b4-15.shared-portfolio-genesis@v1` | `market-os.b4-18.shared-portfolio-genesis@v2` |
| Policy | `market-os.b4-1.paper-broker@v1.policy` | `market-os.b4-18.paper-broker@v2.policy` |
| Event ledger | `market-os.b4-1.paper-portfolio-event@v1` | `market-os.b4-18.paper-portfolio-event@v2` |
| Snapshot/checkpoint | `market-os.b4-1.portfolio-snapshot@v1` | `market-os.b4-18.portfolio-snapshot@v2` |

These are internal Market OS identities. They are not exchange or provider wire
schemas. A later target version must be a separate contract, not an implicit
extension of this one.

## Required migration phases

1. **Preflight:** recover the source with the existing read-only broker, verify
   schema identity, policy fingerprint, ledger sequence, hash chain, snapshots,
   checkpoints, shared membership, reservations, and recovery invariants.
2. **Backup precondition:** create and validate a local immutable B4.11 backup;
   record its manifest and source file fingerprints before transformation.
3. **Plan:** derive a deterministic migration plan from source bytes and pinned
   transformer version. The plan lists every file, record count, source
   fingerprint, target fingerprint expectation, and transform rule.
4. **Copy-on-write transform:** write only to a new temporary destination under
   the same trusted store root. Never modify the source directory.
5. **Destination validation:** validate all target schemas, fingerprints,
   ordering, membership, reservations, checkpoint relation, and path boundaries
   with the target-native v2 recovery validator. Recover the source-shaped
   projection through the current broker as an independent semantic-equivalence
   check; neither validation substitutes for the other.
6. **Replay equivalence:** compare source and target semantic projections. The
   result must preserve portfolio identity, strategy membership, order/fill
   identity, ledger sequence, event cursor, balances, reservations, risk and
   audit outcomes, and deterministic replay meaning.
7. **Promotion:** atomically rename the validated destination to a new
   migration directory while preserving the stable portfolio ID inside the
   target genesis. Validate staging fully before promotion and serialize final
   source recheck and promotion under the source writer lock. Promotion must not
   replace the source. A failed pre-promotion attempt leaves the source
   authoritative and retryable; an interruption after atomic rename is recovered
   by validating the complete promoted destination and returning it on retry.
8. **Evidence:** persist a bounded migration manifest containing source and
   target identities, transformer version, file fingerprints, semantic
   equivalence result, and rollback location.

## Frozen field mapping

The first transformer uses a lossless envelope mapping. Existing allowlisted
fields are copied with their JSON scalar representation unchanged; only the
schema identity is replaced and provenance fields are added. Unknown fields
are rejected. No field is dropped.

| Source file/field | Target file/field | Rule |
|---|---|---|
| `genesis.json` approved identity, wallet, and membership fields | `genesis.json` same fields | Copy unchanged; replace `schema`; add `source_schema` and `source_policy_fingerprint`; set `policy_fingerprint` to the target policy fingerprint. |
| `policy.json` approved policy fields | `policy.json` same fields | Copy unchanged; replace `schema`; add `source_schema`; preserve exact Decimal lexemes. |
| `ledger.jsonl` record `sequence`, `portfolio_id`, `kind`, `payload`, `result`, `idempotency_key`, `previous_event_fingerprint` | Same record fields | Copy unchanged; replace the event schema; add `source_event_fingerprint` and `source_resulting_snapshot_fingerprint`; recompute the target event fingerprint from the target record. |
| `ledger.jsonl` `resulting_snapshot` | Same nested field | Copy every snapshot field unchanged; replace the snapshot schema; add `source_schema`; recompute the target snapshot fingerprint. |
| `checkpoint.json` `sequence`, `snapshot_fingerprint`, `snapshot` | Same fields | Replace checkpoint and nested snapshot schemas; add source fingerprints and recompute target fingerprints. |
| Decimal strings, timestamps, cursors, members, reservations, orders, fills, audit fields | Same JSON locations | Preserve exact values and ordering. Any malformed or unmapped value rejects the migration. |

Target records retain the source fingerprints as provenance. Their target
fingerprints are deterministic hashes of the migrated target records, so a
replay can verify both source identity and target integrity.

## Allowed transformations

The first transformer may only:

- add explicit schema/version fields;
- normalize already-supported scalar representations without changing exact
  decimal meaning;
- make existing shared membership/reservation attribution explicit where the
  source already contains it;
- preserve all event sequence numbers and event fingerprints through a
  documented target fingerprint rule;
- update checkpoint metadata to reference the migrated target snapshot.

It must not invent missing events, infer approvals, reorder events, merge
portfolios, change policy values, alter fills, recalculate prices from wall
clock data, or delete retention history.

## Fail-closed rules

Reject migration when any of the following is true:

- source recovery, backup, or fingerprint validation fails;
- source schema is unsupported or ambiguous;
- a record cannot be mapped by an explicit rule;
- decimal, timestamp, cursor, membership, reservation, or identity values are
  malformed;
- target-native recovery or source-projection replay equivalence fails;
- source and target contain different semantic event/order/fill identities;
- destination or rollback paths escape the selected store root;
- the destination already exists or the source would be overwritten;
- evidence cannot be written atomically.

No partial destination may be promoted. Temporary output may be abandoned for
manual inspection, but the source remains authoritative until promotion is
explicitly completed.

## Idempotency and retry

Migration identity is `(source backup/file-manifest fingerprint, target schema,
transformer version)`. The target directory is a promotion location, not part
of the portfolio identity. Repeating a completed migration with the same
identity returns the existing validated result. Reusing the identity with
different source bytes or transformer code fails with a conflict. A failed run
may be retried only after validating the source again.

## Evidence requirements

The implementation milestone adds regression coverage for:

- isolated and shared genesis migration;
- strategy membership and cash/inventory reservation preservation;
- exact decimal and timestamp preservation;
- source immutability and no in-place replacement;
- malformed/unsupported source rejection;
- checkpoint-without-ledger rejection;
- target fingerprint and replay equivalence;
- destination collision, path traversal, and symlink/reparse rejection;
- fault-injected interruption before promotion and immediately after atomic
  promotion, including retry behavior;
- idempotent retry and conflicting migration identity;
- backup and rollback verification;
- read-only inspection equivalence before and after migration.

Machine-readable evidence uses a new versioned schema and states that the
transformer is implemented locally, the exact source/target schema pair,
counts, fingerprints, replay result, and rollback result. It lists only
unimplemented gates. It must not include secrets or raw private credentials.

## Promotion gate

The field mapping above is frozen for the first local transformer. Migration
remains local and paper-only; connected web access still requires U5.5.
