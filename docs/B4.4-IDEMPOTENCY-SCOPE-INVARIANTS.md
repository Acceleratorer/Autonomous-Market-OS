# B4.4 Idempotency Scope Invariants

**Status:** Implemented locally on 2026-10-26 as a synthetic, paper-only hardening slice.

**Purpose:** Align command retry lookup with the B4.1 contract: an idempotency key is scoped to the portfolio and command type, while the canonical command fingerprint distinguishes payload conflicts within that scope.

## Scope

- Scope order idempotency lookup to `order.accepted`.
- Scope cancel idempotency lookup to `order.cancelled`.
- Scope approval-revocation lookup to `approval.revoked`.
- Permit the same caller key across different command types when each command payload is valid.
- Preserve same-type same-payload replay and same-type different-payload conflict behavior.
- Reject duplicate `(event kind, idempotency key)` identities during recovery.

## Public seams and evidence

The tested seams are `B41Broker.submit_order()`, `B41Broker.cancel_order()`, `B41Broker.revoke_approval()`, and `B41Broker.open()/recover()`. Regression coverage is in [test_portfolio_broker.py](../market_os/tests/test_portfolio_broker.py): shared keys across submit/cancel remain independent, while duplicate persisted command identities fail closed.

## Boundaries

B4.4 does not add a mutation API route, partial fills, expiry, shared portfolios, new persistence, semantic event reduction, provider access, live data, trading, or deployment. The B4.1 contract remains the source of truth for broader command semantics.
