# M2.2: Cited document and retrieval adapter

Status: implemented and verified offline.

Market OS remains the orchestration and safety owner. The adapter is explicitly
selected, isolated from the core dependency set, paper-only, and backed by
synthetic local documents.

## Selection and source seam

LightRAG was selected over RAG-Anything and MiniRAG because it exposes the
smallest text retrieval seam needed by this milestone:

- `LightRAG.ainsert(..., ids=..., file_paths=...)` for stable document identity
  and citation paths.
- `LightRAG.aquery_data(..., QueryParam(mode="naive"))` for structured chunks
  and references without generating an uncited answer.
- `initialize_storages()` and `finalize_storages()` around each isolated run.

Source repository: `D:/Code/Github/company-projects/LightRAG` at commit
`4d0afc1bc36e6a34d4a5895b68efe9413748627a`. LightRAG is MIT licensed. The
reference checkout remained read-only and unchanged.

RAG-Anything was not selected because its document path adds parser,
multimodal, VLM, and LightRAG configuration requirements. MiniRAG remains a
baseline/reference project rather than a second production backend.

### Read-only candidate evaluation

| Repository | Commit | Ingestion/query seam | Offline/dependency finding | Decision |
|---|---|---|---|---|
| LightRAG | `4d0afc1bc36e6a34d4a5895b68efe9413748627a` | `ainsert` + `aquery_data` | Deterministic injected tokenizer, embeddings, and LLM run locally | Selected |
| RAG-Anything | `da6e2d87a7d3f2746c4541f59953b8764213f6a2` | `process_document_complete` + `aquery` | Adds parser/VLM and LightRAG setup; offline tokenizer cache is required | Deferred |
| MiniRAG | `e204d239421f45004852953679927fdf6733f236` | `ainsert` + `aquery` | Small baseline, but reserved as reference rather than production backend | Deferred |

All three repositories were MIT licensed and clean before and after
evaluation. No source tree was copied or modified.

LightRAG persists its own file-backed KV, vector, graph, and document-status
stores under an isolated `working_dir`; the adapter never treats those files
as Market OS state. RAG-Anything's `process_document_complete` delegates into
that LightRAG storage plus parser/output directories and optional VLM/model
services. MiniRAG's `MiniRAG.insert`/`query` path similarly requires its own
storage and embedding/LLM functions. These persistence and dependency
differences are why only LightRAG's narrow child-process seam is integrated.

#### LightRAG — selected

- Package/entry points: `lightrag`; `LightRAG.ainsert`,
  `LightRAG.aquery_data`, `initialize_storages`, and `finalize_storages`.
- Document types: text/Markdown through the SDK seam; broader native/parser
  formats exist but are outside this adapter.
- Metadata/citations: caller-supplied `ids` and `file_paths`; structured
  chunks expose `chunk_id`, `file_path`, and `reference_id`.
- Persistence: four file-backed storage families under `working_dir`; the
  adapter isolates and deletes that child workspace after normalization.
- Embedding/model requirements: LightRAG requires callable LLM and embedding
  functions, but this milestone injects deterministic local functions and a
  character tokenizer; no model service is contacted.
- Network/import behavior: default tokenizer/model bindings can require
  network or caches; injected functions avoid that path. Import-time `.env`
  loading is confined to the child process.
- Failure/deadline behavior: child exit, malformed envelopes, cancellation,
  and provider deadlines are normalized by the adapter; LightRAG storage
  failures surface as provider failures.

#### RAG-Anything — deferred

- Package/entry points: `raganything`; `process_document_complete`,
  `insert_content_list`, `aquery`, and `aquery_with_multimodal`.
- Document types: text, Markdown, PDF, images, Office documents, tables,
  equations, audio, and video through parser/modal processors.
- Metadata/citations: `doc_id`, `file_path`, callbacks, and inherited
  LightRAG chunk/reference metadata; richer multimodal asset metadata is
  parser-specific.
- Persistence: LightRAG stores plus parser/output directories and optional
  multimodal asset paths.
- Embedding/model requirements: LLM, embedding, and for multimodal paths VLM,
  OCR/parser, audio/video, and optional external model services.
- Network/import behavior: the source documents an offline `tiktoken` cache
  requirement; configured hosted/local model bindings may still use network.
- Failure/deadline behavior: document processing raises runtime errors and
  leaves failed document status for retry; batch/parser/model timeouts remain
  provider-specific and are not root-owned here.

#### MiniRAG — reference baseline

- Package/entry points: `minirag`; `MiniRAG.insert`/`ainsert` and
  `MiniRAG.query`/`aquery`.
- Document types: text strings and text-file/API ingestion in its server
  layer; no selected multimodal production seam here.
- Metadata/citations: chunk `full_doc_id` and graph/vector `source_id` values
  are available, but there is no selected normalized citation envelope
  equivalent to LightRAG's structured references.
- Persistence: JSON/KV, vector, and graph backends configured by the package;
  the API layer owns additional server state.
- Embedding/model requirements: injected or configured embedding and LLM
  functions, commonly local Ollama/Lollms or hosted bindings.
- Network/import behavior: local execution is possible with injected models,
  while default bindings may contact local or remote model services.
- Failure/deadline behavior: async model/storage failures propagate through
  the package; no root-owned provider deadline or cancellation seam was
  established, so it remains a benchmark/reference choice.

## Fixture corpus and normalized contract

`market_os/tests/fixtures/lightrag/corpus.json` contains four synthetic local
documents: an ETF factsheet, market commentary, a paper-trading risk policy,
and an earnings-style note. Every document has a stable ID, title, publisher,
source reference, timestamps, symbols, media type, SHA-256 content hash,
synthetic-internal license classification, and `Provenance`.

The adapter rejects duplicate IDs, empty content, unsupported media types,
hash mismatches, invalid UTC timestamps, unknown license classification, and
missing provenance. Retrieval results normalize query, document IDs, passage
IDs, excerpts, citation references, provider identity/version, retrieval time,
query fingerprint, content fingerprints, and partial/error state.

## Workflow behavior

Use `--provider lightrag --backtest-provider vibe-trading` explicitly. The
workflow loads market evidence, selects matching documents, runs LightRAG in an
isolated child process with deterministic local tokenizer/embedding/LLM
functions, persists document and retrieval artifacts, links evidence and
research lineage, runs the existing Vibe-Trading backtest, and returns a
paper-only order plan and risk decision.

The default fixture workflow is unchanged. LightRAG failures do not fall back
to another retrieval engine. Child cancellation and provider deadlines are
enforced by the root-owned adapter boundary.

## Limitations

- The adapter supports LightRAG text ingestion and naive chunk retrieval only;
  graph modes, multimodal parsing, reranking, and generated answers are out of
  scope.
- LightRAG dependencies remain outside Market OS core installation and must be
  provided in an isolated environment.
- Temporary child storage is removed after each adapter call; normalized root
  artifacts retain the durable document and retrieval lineage.
