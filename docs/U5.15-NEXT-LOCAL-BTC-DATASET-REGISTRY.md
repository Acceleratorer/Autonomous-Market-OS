# U5.15 Next.js Local BTC Dataset Registry

**Status:** Implemented locally on 2026-10-29.  
**Scope:** Add a bounded, read-only BTC history catalog to the existing local
Next.js operator.

## Contract

- `GET /v1/btc/history/datasets` lists existing B1 dataset metadata in stable
  revision order. `limit` is 1–100 (default 25); the exclusive cursor is
  `after_dataset_revision`.
- The endpoint uses only the gateway's configured local HistoryStore. It does
  not accept a caller-provided store path.
- If the store does not exist, the endpoint returns an empty page without
  creating its root, DuckDB catalog, or data directories. Existing catalogs
  open in DuckDB read-only mode.
- The response includes the revision, market identity, interval, candle count,
  observed UTC range, and canonical fingerprint. It omits filesystem paths and
  raw page details. Catalog timestamps outside the supported UTC ISO date range
  are rejected as store-integrity errors before they reach the renderer.
- An existing `btc-history` path must be a local directory; malformed store
  paths are reported as integrity errors instead of an empty catalog.
- The Next.js `/datasets` route renders the bounded page on the server and
  validates every response field and pagination boundary. Page links remain
  ordinary GET navigation.
- The page shows catalog metadata only. It does not read Parquet candles,
  verify stored-file hashes, replay a dataset, acquire history, or call a
  provider. Replay remains the integrity check for stored files.

## Design

The registry follows the local operator's dark, dense, system-font design
brief. It uses a labelled scroll region for the wide metadata table, a visible
local/read-only boundary, and no client-side state or decorative motion. This
keeps the interface consistent with the portfolio inspection workflow and
avoids loading GSAP or external font assets for static catalog rows.

## Remaining limits

- This registry is local and read-only. Connected deployment still requires
  U5.5 decisions for target, identity, tenant/storage isolation, sessions,
  rate limits, audit, backup/rollback, observability, and operator access.
- Catalog entries are not proof that the referenced Parquet files remain
  intact. Use the existing replay check before treating a dataset as validated.
- Ingestion-manifest inspection and experiment views remain later web slices;
  they need their own bounded response contracts before exposure. U5.16 adds
  the separate bounded candle detail contract.
