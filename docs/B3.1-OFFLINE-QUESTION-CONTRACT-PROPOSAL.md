# B3.1 Offline Question-Contract Proposal

**Status:** Proposal only; no implementation or evaluation is authorized.
**Scope:** BTCUSDT Spot, recorded fixtures, and the three B3.1 questions frozen
by [ADR-0022](decisions/ADR-0022-b3-1-decision-freeze.md).

This document recommends internal Market OS fixture contracts for the three
questions. The IDs, schemas, labels, and validation details below are
recommendations for human review. They are not frozen decisions, API contracts,
provider requests, or TypeSafe wire claims. B3.1 remains recorded-fixture-only;
this proposal authorizes no code, provider or Binance request, credential use,
context egress, data acquisition, paper execution, or trading.

## 1. Frozen boundary, recommendations, and open choices

### Frozen by ADR-0022

- Jev is advisory and evaluates evidence support, agreement versus
  contradiction, and abstention. Consistency, freshness, provenance, and
  evidence-quality gates remain deterministic Market OS responsibilities.
- The research scope is BTCUSDT Spot-only. Preserve B2's five-minute log
  return and its positive versus non-positive target. Executable net return is
  a separate economic target. Jev assessment probabilities are not market
  return probabilities.
- Work and evaluation remain recorded-fixture-only. No provider request,
  credential, provider adapter activation, context egress, acquisition,
  implementation, prospective study, paper execution, or trading is authorized.
- B3's existing E1/E2 definitions, fixture, results, offline status, and
  non-promotion remain unchanged.
- This proposal defines no new benchmark arm or evaluation scope. Future arm
  descriptions elsewhere remain conceptual and require separate decisions.

### Recommendations in this proposal

- Version each logical question independently; keep its label distribution
  scoped to that question and its stable packet hypothesis IDs.
- Use a packet-level normalized assessment that retains each result and its
  status. Never combine unlike question distributions into one score or
  probability.
- Keep validation and eligibility decisions deterministic in Market OS. A
  syntactically valid Jev answer does not certify truth, freshness, provenance,
  consistency, quality, or use eligibility.
- Add fixtures for the full behavior matrix in Sections 6–7, including valid
  disagreement and concentrated-but-valid answers.

### Human choices that remain open

- Approval of these names, versions, precise question wording, label meanings,
  distribution tolerance, and abstention rules.
- Whether to adopt the proposed packet/result field shapes and status
  precedence, and how raw fixture material may be retained or redacted.
- The exact local fixture serialization, canonical fingerprint projection,
  timestamp policy for simulated fixture responses, and evidence-reference
  requirements.
- Any future provider, primitive, request-count, privacy, retention, cost, or
  latency mapping. This proposal makes no assertion about TypeSafe wire support
  or how many provider requests would represent the three logical questions.

## 2. Proposed internal identities

All values below are proposed internal identifiers. They are not public API
versions or provider schemas.

| Contract item | Proposed identifier | Purpose |
|---|---|---|
| Packet schema | `market-os.btc-b3-1.evidence-packet.v1` | Immutable BTCUSDT Spot packet for fixture assessment. |
| Normalized assessment schema | `market-os.btc-b3-1.normalized-assessment.v1` | Market OS envelope for the three logical results and deterministic status. |
| Packet configuration ID | `btc.b3-1.packet.v1` | Pins packet fields, allowed input classes, and canonical fingerprint rules. |
| Normalized-assessment configuration ID | `btc.b3-1.normalized-assessment.v1` | Pins all three question IDs/versions, label sets, probability rules, and normalization rules. |

| Question ID | Proposed question version | Bounded purpose |
|---|---|---|
| `market-os.btc.b3-1.evidence-support` | `market-os.btc.b3-1.evidence-support.v1` | Assess how supplied, eligible evidence bears on each identified hypothesis. |
| `market-os.btc.b3-1.agreement-contradiction` | `market-os.btc.b3-1.agreement-contradiction.v1` | Assess agreement or contradiction only among the packet's comparable hypotheses. |
| `market-os.btc.b3-1.abstention` | `market-os.btc.b3-1.abstention.v1` | Assess whether the supplied packet supports an advisory answer to the first two questions, or warrants abstention. |

The packet configuration would pin the packet schema and configuration IDs,
BTCUSDT Spot scope, B2 feature and target-definition identities, and the
question-set reference. The normalized-assessment configuration would pin the
assessment schema and configuration IDs plus the exact three question
versions. Changing a question's purpose, scope, labels, selected-label rule,
or probability meaning requires a new question version and configuration
fingerprint. It must not rewrite an existing packet or fixture.

## 3. Shared result and probability rules

Each question result has one of two shapes:

- **Answered:** exact question ID/version, scope references, one selected
  label, a probability for every label in that question's exact label set, and
  any required packet evidence/hypothesis references.
- **Abstained:** exact question ID/version, `selected_label: null`,
  `probabilities: null`, and a bounded reason code. Do not fabricate a neutral,
  uniform, or zero distribution for an abstention.

For Question 1, the packet pins a non-empty `assessment_hypothesis_ids` list.
Market OS computes this list before fixture evaluation as every candidate
hypothesis with a bounded claim, target, horizon, and at least one resolvable
evidence reference whose deterministic eligibility gate passes. The list is
canonical, unique, and fingerprinted with the packet. Every listed hypothesis
must be represented exactly once as either answered or explicitly abstained;
candidates outside the list remain visible with their deterministic exclusion
reason and receive no Jev result. This allows partial coverage without
confusing one hypothesis's refusal with a semantic label or omitting it from
the record. For Question 2, each pair in the deterministic pair set receives
one answered or explicitly abstained Jev result. An empty pair set has no Jev
question answer; Market OS records the scope as not applicable. Question 3 has
one packet-level answered or abstained result.

For an answered result, probabilities are finite numbers in `[0, 1]`, keys
match the full label set exactly, and values sum to one within an absolute
tolerance of `1e-6`. Do not silently renormalize. `selected_label` must be the
unique maximum-probability label. A tie requires an explicit question-level
abstention with reason `ambiguous_distribution`; a tied distribution must not
be resolved by field order. Probability values are conditional semantic
judgments about the supplied packet and declared question scope. They are not
frequencies, calibrated correctness probabilities, `P(return_5m > 0)`,
expected return, an economic edge, or a risk limit. Concentration and any
confidence-like diagnostic are not evidence of correctness.

Question results refer only to the immutable packet fingerprint and its
pre-existing hypothesis IDs. An answer cannot add, rename, or repair a
hypothesis. References to evidence must resolve to packet evidence references;
free text cannot substitute for a reference. The normalizer preserves the
question distributions separately and does not average, multiply, rank, or
pool probabilities across questions.

## 4. Question contracts

### 4.1 Evidence support

- **Question ID/version:** `market-os.btc.b3-1.evidence-support`, version
  `market-os.btc.b3-1.evidence-support.v1`.
- **Bounded purpose:** For each assessment hypothesis in the packet's pinned
  `assessment_hypothesis_ids` list, judge whether only the
  evidence references supplied with the packet support that hypothesis. This
  does not decide whether the hypothesis is true, whether its market forecast
  is calibrated, or whether its evidence is fresh or trustworthy; those gates
  remain with Market OS.
- **Exact labels:** `supported`, `mixed`, `unsupported`.

| Label | Meaning |
|---|---|
| `supported` | Supplied evidence materially supports the stated hypothesis within its declared target and horizon. |
| `mixed` | Supplied evidence contains material support and limitation or counterevidence, or only partial support. |
| `unsupported` | Supplied evidence does not materially support the hypothesis. This is not proof that the hypothesis is false. |

- **Selected-label rule:** One result per ID in the packet's pinned
  `assessment_hypothesis_ids`; choose the unique maximum of that hypothesis's
  three-label distribution. Include only evidence references already present
  in the packet. The result must not
  compare one hypothesis with another; that is Question 2.
- **Distribution semantics:** `P(supported | packet, hypothesis_id)`,
  `P(mixed | packet, hypothesis_id)`, and
  `P(unsupported | packet, hypothesis_id)`. These are semantic assessment
  probabilities over these three labels only.
- **Valid abstention:** The question may abstain for a hypothesis with a
  bounded reason such as `insufficient_evidence`, `ambiguous_distribution`, or
  `scope_unclear`. Preserve the hypothesis ID and reason; do not assign a
  fallback probability. An abstention for one hypothesis does not invent a
  result for another.
- **Invalid/unsupported/inconsistent/stale/unavailable:** Apply the shared
  statuses and precedence in Section 5. Unknown hypothesis/evidence IDs or
  duplicate/missing required hypothesis results are internally inconsistent;
  unknown question versions or labels are unsupported; malformed result
  shapes are schema-invalid. Stale packet/response is stale. Missing fixture
  response is unavailable. None becomes `unsupported` as a semantic label.
- **Hypothesis IDs:** Cover the packet's required hypotheses exactly once;
  each entry is either answered or explicitly abstained. IDs must be
  byte-for-byte stable packet IDs; sort only for deterministic serialization,
  never as evidence ranking. A whole-question refusal is represented by
  abstained entries for every required hypothesis.
- **Deterministic Market OS validation:** Verify packet fingerprint, allowed
  evidence-reference membership, hypothesis uniqueness and completeness,
  time/target leakage boundaries, provenance, freshness, units and schema.
  These checks do not answer whether the evidence semantically supports a
  hypothesis.
- **Required fixtures:** The shared per-question fixture matrix in Section 6
  applies. Evidence-support disagreement must include a valid packet where
  different hypotheses receive different labels and a valid `mixed` result
  with both supporting and challenging references. A concentrated-but-valid
  answer must use a unique maximum, such as `{supported: 0.99, mixed: 0.005,
  unsupported: 0.005}`, and remain valid.

### 4.2 Agreement versus contradiction

- **Question ID/version:** `market-os.btc.b3-1.agreement-contradiction`,
  version `market-os.btc.b3-1.agreement-contradiction.v1`.
- **Bounded purpose:** For each canonical pair of comparable packet
  hypotheses, assess whether the two claims agree, contradict, or have a mixed
  relationship. Each answer is pair-scoped; the contract does not aggregate
  across pairs. Comparability is established
  by deterministic Market OS rules over target, event definition, horizon,
  direction, units, and timing before interpretation. Jev does not decide that
  mismatched targets are contradictory.
- **Exact Jev labels:** `agreement`, `contradiction`, `mixed`.

| Label | Meaning |
|---|---|
| `agreement` | The referenced comparable claims support compatible outcomes for the same declared event and horizon. |
| `contradiction` | The referenced comparable claims make mutually incompatible claims for the same declared event and horizon. |
| `mixed` | For this pair, supplied evidence supports elements of both agreement and contradiction, or leaves the relationship materially ambiguous. |

- **Selected-label rule:** The packet supplies a deterministic, canonical list
  of comparable hypothesis ID pairs (each pair sorted lexicographically and
  the pair list sorted). Produce exactly one Jev result for each pair and
  select the unique maximum among the first three labels. When the list is
  empty, Market OS records `not_applicable` with reason `no_comparable_claims`, a
  null selected label, and no distribution; no Jev answer is requested or
  inferred. Jev cannot create comparison pairs or infer missing hypotheses.
- **Distribution semantics:** For each pair `p`, `P(agreement | packet, p)`,
  `P(contradiction | packet, p)`, and `P(mixed | packet, p)`. These semantic
  assessment distributions do not measure the probability that either market
  claim is true. The `not_applicable` scope status for an empty pair set is
  deterministic Market OS metadata and has no Jev distribution.
- **Valid abstention:** Each Jev pair result may explicitly abstain with a bounded
  reason such as `insufficient_evidence`, `ambiguous_distribution`, or
  `scope_unclear`; preserve the pair ID and reason and do not substitute
  `not_applicable` for uncertainty. An empty pair set is deterministically
  `not_applicable` and does not require a Jev abstention.
- **Invalid/unsupported/inconsistent/stale/unavailable:** Apply Section 5.
  Invalid or missing pair IDs, a different pair set from the packet, or
  duplicated pairs are internally inconsistent. `not_applicable` is valid
  only when the deterministic pair set is empty. Unknown versions or
  labels are unsupported. Missing response is unavailable; an expired packet
  or result is stale.
- **Hypothesis IDs:** Every comparison result references exactly one canonical
  packet pair; each pair contains two distinct IDs, appears once, and the full
  result set matches the deterministic pair list. `not_applicable` is valid
  only for the empty list; it must not omit eligible pairs to force that
  status.
- **Deterministic Market OS validation:** Compute and fingerprint eligible
  comparison pairs from the packet, validate target/horizon/unit compatibility,
  and check all cited IDs, provenance, timestamps, and freshness. The gate
  validates the comparison domain; it does not supply Jev's semantic
  agreement/contradiction answer.
- **Required fixtures:** The shared matrix applies. The disagreement fixture
  must contain at least one comparable hypothesis pair with an actual direction
  conflict and a valid per-pair `contradiction` or `mixed` result. This is a
  valid semantic result, not a parser rejection. The concentrated-but-valid
  fixture must retain a unique maximum over the exact Jev label set, e.g.
  `{agreement: 0.005, contradiction: 0.99, mixed: 0.005}` for that pair.

### 4.3 Abstention

- **Question ID/version:** `market-os.btc.b3-1.abstention`, version
  `market-os.btc.b3-1.abstention.v1`.
- **Bounded purpose:** Decide whether the supplied packet permits an advisory
  response to Questions 1 and 2 or whether the evaluator recommends
  abstention. This is not a trading, risk, data-quality, or execution decision.
- **Exact labels:** `answerable`, `recommend_abstention`.
- **Selected-label rule:** One packet-level result. Select the unique maximum
  of the two-label distribution. It may reference only existing packet
  hypothesis IDs as its basis; an empty basis is allowed when the reason is
  packet-level and fully specified.
- **Distribution semantics:** `P(answerable | supplied packet, Questions 1
  and 2)` and `P(recommend_abstention | supplied packet, Questions 1 and 2)`.
  This is a semantic assessment distribution, not correctness, confidence in
  Market OS gates, or market probability.
- **Valid abstention:** A question-level refusal to answer Question 3 itself
  uses the shared `abstained` result shape with a reason code. A normal,
  answered result selecting `recommend_abstention` is different: it is a valid
  answer recommending that semantic conclusions from Questions 1 and 2 be
  withheld. Neither form may silently become `answerable` or a neutral
  probability.
- **Invalid/unsupported/inconsistent/stale/unavailable:** Apply Section 5.
  Unknown basis IDs or inconsistent selected label/distribution are
  internally inconsistent. Unknown labels or versions are unsupported. A
  malformed abstention without a bounded reason is schema-invalid. Stale
  packet/response is stale; absent recorded response is unavailable.
- **Hypothesis IDs:** This is packet-level, not a fabricated per-hypothesis
  answer. Any basis IDs must be existing, unique packet hypothesis IDs. It
  must not add IDs or rewrite Questions 1–2 results.
- **Deterministic Market OS validation:** Enforce packet readiness, source
  availability, target-leakage exclusions, provenance, freshness, and
  evidence-quality rules independently. A Jev `answerable` label cannot
  override a failed gate; a Jev `recommend_abstention` label is preserved as an
  advisory assessment.
- **Required fixtures:** The shared matrix applies. The disagreement fixture
  uses a packet with contradictory comparable hypotheses and a valid
  `recommend_abstention` result; this remains a valid answer, not a validation
  failure. The concentrated-but-valid case can use
  `{answerable: 0.005, recommend_abstention: 0.995}` and must remain a valid
  advisory output while having no independent execution effect.

## 5. Invalid, unsupported, stale, and unavailable behavior

Proposed normalized `assessment_status` values are:

1. `schema_invalid` — malformed fixture/result shape, missing required
   fields, wrong primitive value type, or invalid encoding.
2. `unsupported` — unknown packet/question/configuration version, label set,
   or unsupported contract identity.
3. `internally_inconsistent` — parseable values violate cross-field rules,
   such as selected label not being the unique maximum, wrong probability sum,
   wrong or duplicate hypothesis/pair IDs, or mismatched packet identity.
4. `stale` — packet or otherwise-valid response is beyond its explicit
   freshness/expiry boundary at the declared fixture use time.
5. `unavailable` — no matching fixture response exists, response is explicitly
   absent, or a recorded response is late relative to a pinned local fixture
   deadline. Preserve cause (`missing_fixture`, `response_absent`, or
   `response_late`) without claiming observed provider latency.
6. `abstained` — a valid explicit evaluator refusal on at least one required
   question, one required hypothesis entry in Question 1, or one required pair
   in Question 2. Preserve all valid sibling results, the abstaining
   question/hypothesis/pair IDs, and bounded reason codes; it is not a zero or
   neutral answer.
7. `usable` — all three question scopes are complete and contract-valid,
   contain no abstained required entries, are within their declared fixture
   freshness windows, and are tied to the same valid packet. Question 2 is
   complete when every canonical pair has an answered result, or the empty
   pair set has its deterministic `not_applicable` scope status. This means
   only that the normalized fixture assessment is usable for offline semantic
   analysis. It confers no signal or execution authority.

Precedence recommendation when multiple conditions occur: malformed shape is
`schema_invalid`; unsupported identity/labels is `unsupported`; cross-field
violations are `internally_inconsistent`; expired inputs/results are `stale`;
missing or late fixture responses are `unavailable`; explicit valid refusal
on any required question or scoped hypothesis/pair entry is `abstained`;
otherwise `usable`. Preserve the underlying case kind and reason
alongside the normalized status. A valid contradiction, mixed answer, valid
abstention recommendation in Question 3, or concentrated distribution is not
by itself an invalid status.

For any non-usable status, preserve question-level results that were valid,
but never synthesize missing labels, probabilities, neutral values, or
fallback-provider answers. A deterministic Market OS gate failure remains
visible as a separate validation result and blocks future use regardless of a
Jev answer. The gate result is not written as if Jev supplied it.

## 6. Required per-question fixture matrix

Each of the three question versions should have an independently addressable
fixture case for every row below. Cases should pin the packet fingerprint,
question ID/version, fixture ID, and expected normalized status. For cases that
depend on multiple hypotheses or pairs, the fixture packet must contain the
minimum stable IDs needed to exercise that condition.

| Fixture case kind | Evidence support | Agreement/contradiction | Abstention | Expected behavior |
|---|---|---|---|---|
| `valid` | One or more complete per-hypothesis results. | One complete Jev result per deterministic pair; an empty pair set is `not_applicable`. | One packet-level result. | Exact IDs, labels, probability rules, and freshness pass. |
| `malformed` | Missing field, wrong JSON type, or malformed result shape. | Malformed pair/result shape. | Missing reason or wrong result shape. | `schema_invalid`; no guessed defaults. |
| `unsupported` | Unknown label or question version. | Unknown label or question version. | Unknown label or question version. | `unsupported`; do not alias or coerce. |
| `inconsistent` | Selected label differs from unique maximum, wrong sum, duplicate/missing/unknown hypothesis ID. | Selected-label mismatch, wrong sum, or invalid/duplicate pair set. | Selected-label mismatch, wrong sum, or unknown basis ID. | `internally_inconsistent`; do not normalize away. |
| `stale` | Packet or assessment is beyond explicit freshness window. | Packet or assessment is beyond explicit freshness window. | Packet or assessment is beyond explicit freshness window. | `stale`; preserve expiry and compared times. |
| `unavailable` | No matching fixture or explicit absent response. | No matching fixture or explicit absent response. | No matching fixture or explicit absent response. | `unavailable`; probabilities remain absent. |
| `abstaining` | Explicit refusal for one or more pinned hypotheses, each with a bounded reason. | Explicit refusal for one or more canonical pairs, each with a bounded reason. | Explicit refusal to answer Q3, distinct from its `recommend_abstention` label. | `abstained`; preserve the refusal and valid sibling results. |
| `disagreement` | Different valid labels across hypotheses and a valid `mixed` evidence case. | Valid per-pair `contradiction` or `mixed` answer for conflicting comparable claims. | Conflicting comparable claims with valid `recommend_abstention` answer. | Valid semantic disagreement; not rejected as an integrity error. |
| `concentrated_valid` | Unique maximum such as 0.99 on one support label. | Unique per-pair maximum such as 0.99 on contradiction for a conflicting pair. | Unique maximum such as 0.995 on `recommend_abstention`. | Remains valid; concentration is diagnostic and is never a rejection reason. |

Also include a combined fixture in which all three results are valid and
disagreement is represented in the question answers. It must replay to the
same normalized artifact and fingerprint. Fixture timestamps are declared
simulation values, not measured latency or provider service behavior.

## 7. Proposed fixture taxonomy

Proposed case kinds for B3.1 fixtures:

- `valid`
- `malformed`
- `unsupported`
- `inconsistent`
- `stale`
- `unavailable`
- `late` (source case kind; normalize to `unavailable` with cause
  `response_late`)
- `abstaining`
- `disagreement`
- `concentrated_valid`

Case kind describes what the fixture is designed to exercise; normalized
assessment status describes the deterministic result. Thus a `disagreement`
case can normalize to `usable`, and `concentrated_valid` must normalize to
`usable` when all other conditions pass. Keep `hostile` as a separately
versioned adversarial fixture only if a later reviewer defines a bounded
hostile-input scope; it is not an additional Jev question or label. Do not
inherit B3's case taxonomy as a wire contract or alter B3's existing fixture.

## 8. Normalizing three results without market-probability semantics

One normalized assessment should be a deterministic envelope containing:

- proposed schema and normalized-assessment configuration IDs;
- packet schema/configuration IDs, observation ID, packet fingerprint, and
  pinned question-set fingerprint;
- exactly one keyed result for each proposed question ID/version. Evidence
  support contains one Jev result per pinned assessment hypothesis;
  agreement/contradiction contains one Jev result per canonical pair or a
  deterministic `not_applicable` scope status for an empty pair set;
  abstention contains one Jev result at packet level. Each Jev result carries
  its own `answered` or `abstained` outcome, selected label, exact-label
  distribution or null, and stable packet hypothesis/evidence references; the
  empty-set scope status is deterministic Market OS metadata.
- assessment status, deterministic validation outcomes, bounded failure or
  abstention reasons, fixture/case identities, and response fingerprint when
  present.

The normalizer copies the three independent distributions under their
question-specific IDs. It does not calculate a combined distribution or
scalar. A valid Question 3 result selecting `recommend_abstention` is retained
as that question's semantic result. Any later policy must separately decide
whether that recommendation makes Jev-derived features ineligible; this
proposal defines no signal policy. For this fixture-only milestone, no Jev
result enters a Market OS signal or execution path.

The normalized assessment is not a market prediction. To evaluate B2's
positive/non-positive five-minute return later, a separately approved
chronological calibration/fusion procedure would need realized outcomes kept
outside the packet, with the frozen Platt and regularized-logistic primary
methods. Executable net return remains a separate target. No category
probability, Question 3 recommendation, confidence, or concentration is
relabeled as either target probability.

## 9. Compatibility with existing B3 E1/E2

| Existing B3 item | Compatibility mapping |
|---|---|
| E1 numerical B2 conditional-rate arm | Unchanged. It has no Jev question result and receives no synthetic B3.1 assessment. |
| E2 numerical inputs plus one recorded typed assessment | Unchanged. Existing `btc_5m_market_assessment` options `bullish`, `bearish`, `indeterminate`, probabilities, fixture, metrics, and results keep their current meaning. |
| Proposed B3.1 three-question results | New, separately versioned semantic assessment. There is no lossless mapping from `bullish`/`bearish`/`indeterminate` into evidence support, agreement/contradiction, or abstention. Do not relabel or backfill B3 records. |
| Future comparative evaluation | Any later use requires a separate approved protocol and arm/configuration identity. Preserve E1/E2 artifacts and matched-control definitions. |

This mapping is documentary compatibility only; it changes no existing B3
fixture, artifact, code, API, score, or promotion decision. See the [B3
benchmark report](U3-B3-JEV-INCREMENTAL-BENCHMARK-REPORT.md), [ADR-0019](decisions/ADR-0019-u3-b3-jev-experimental-boundary.md),
and the B3 section of [API contracts](api/contracts.md).

## 10. Acceptance criteria for a later offline scaffold

A separately authorized implementation milestone should be accepted only when
all of the following hold:

1. **Scope:** It reads local recorded fixtures only. It makes zero provider,
   network, credential, exchange, or data-acquisition requests; adds no
   provider adapter activation, execution path, paper trading, or API surface.
2. **Pinned contracts:** It implements only human-approved schema/config and
   question versions with exact label sets and strict unknown-version/label
   rejection. It asserts no unapproved provider primitive mapping.
3. **Packet integrity:** It validates the packet fingerprint and identity,
   BTCUSDT Spot scope, B2 feature/target-definition lineage, hypothesis IDs,
   evidence references, and point-in-time readiness/freshness rules before
   accepting results. Realized targets, future references, fills, account
   state, or outcome-derived fields are rejected from the packet.
4. **Question integrity:** It enforces each selected-label rule, complete
   finite probability distribution and pinned sum tolerance, explicit
   abstention shape, exact stable hypothesis/pair references, and the
   question-specific bounded scope. It never turns a missing result into a
   neutral probability.
5. **Statuses:** It deterministically distinguishes schema-invalid,
   unsupported, inconsistent, stale, unavailable/late, abstained, and usable
   outcomes with the approved precedence and reason codes. Valid disagreement
   and concentrated-but-valid outputs remain accepted.
6. **Normalization:** It stores all three results and statuses separately in
   the one normalized assessment. It does not pool them into a market
   probability, candidate signal, policy decision, or execution input.
7. **Fixtures and replay:** Every fixture case in Sections 6–7 is covered by
   focused offline tests; repeated runs over the same canonical fixture yield
   identical normalized bytes, fingerprints, statuses, and lineage. Offline
   usage/cost/latency are unknown or not observed, never zero-observed claims.
8. **Compatibility and review:** B3 E1/E2 artifacts, tests, API contracts,
   provider adapters, and existing reports remain unchanged. A code review
   confirms document-approved scope and no accidental external side effects.

These are proposed acceptance criteria, not authorization to start the
scaffold. Implementation and any later study require the applicable human
decision and remain subject to ADR-0022's restrictions.
