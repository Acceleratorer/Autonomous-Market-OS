# U5.1 Local Service Boundary

**Status:** Implemented and verified locally on 2026-10-28.
**Scope:** Synthetic, paper-only local HTTP boundary hardening.

## Contract

- `market_os serve` binds only to a loopback host; remote bind addresses fail before a listener is created.
- Every GET and POST request must carry a loopback `Host` value. Other host values receive HTTP 403 before route handling.
- Browser POSTs must be same-origin: if `Origin` is present, it must match the HTTP scheme, host, and port; if `Sec-Fetch-Site` is present, it must be `same-origin`. Origin-free local CLI and server-to-server clients remain supported.
- POST bodies require one bounded non-negative `Content-Length`, do not accept `Transfer-Encoding`, and are capped before they are read: 1 MiB generally and 32,768,000 bytes for the bounded local BTC fixture-ingest route. Truncated or non-object JSON bodies are rejected.
- Legacy BTC history and connectivity inspection opens existing stores read-only. Inspecting a missing store returns 404 without creating its directory or catalog.
- Startup recovery completes before the HTTP listener is opened and before readiness can be served.
- Structured request logs store the URL path without query parameters, along with method, status, run ID, and error type.
- Existing API routes and local paper-only behavior remain unchanged.

## Verification

Regression tests cover rejection of non-loopback bind, malformed or untrusted `Host` values, cross-origin POSTs, oversized POSTs, non-creating history/connectivity reads, omission of query values from the service log, and recovery failure before listener creation. Service and wrapper integration tests verify the ordinary local startup/readiness path.

## Remaining boundary

Loopback binding is local access control, not user authentication. Shared access still requires authenticated identity, authorization, tenant isolation, production logging/retention, and a separately reviewed deployment. The B4 HTTP surface remains GET-only.
